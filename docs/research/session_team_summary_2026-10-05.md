# ConflictDynamics — 이번 세션 작업 요약

작성일: 2026-10-05 · 팀 공유용

**이번 세션에서는 AI 직원 20명이 일하고 대화하는 시뮬레이션의 비용 원인을 조사하고, 반복 검색 계산을 줄이는 기능을 구현했습니다. 또한 기업 갈등 개입 방식을 검토해 다음 실험안을 정리했습니다.**

확인된 성과는 **시험용 실행에서 검색 계산을 약 절반 줄이면서 결과를 유지했다는 것**입니다. 실제 유료 API의 토큰·비용 절감과 갈등 개입 효과는 아직 검증하지 않았습니다.

## 먼저 알아둘 용어

- **LLM 호출:** AI에게 계획·행동·발언 등을 생성해 달라고 요청하는 것.
- **토큰:** AI가 읽고 생성하는 텍스트를 세는 단위. API 비용과 관련됩니다.
- **Embedding:** 문장을 숫자 목록으로 바꾸는 계산. 기억 중 관련 내용을 찾을 때 사용합니다.
- **Cache:** 이전 계산 결과를 저장해 같은 계산을 반복하지 않는 장치.
- **Tick:** 시뮬레이션의 한 시간 단계. 이 프로젝트에서는 15분입니다.
- **Demo:** 실제 유료 AI 대신 정해진 규칙을 사용하는 시험 실행. 프로그램의 일관성을 검사할 수 있지만 실제 AI의 비용·행동을 대표하지는 않습니다.

## 1. 토큰 효율화: 조사 → 구현 → 실제 검증 준비

| 단계 | 한 일 | 결과와 의미 |
|---|---|---|
| 1차: 비용 원인 진단 | 실제 코드에서 AI 호출 경로를 추적하고, 누가·언제·왜 호출했는지 기록하는 기능 추가 | 계획, 행동, 대화, 기억 검색·쓰기, 회고 등을 구분해 이후 분석 가능 |
| 2차: 세 가지 후보 비교 | 긴 반복 입력, 행동 재시도, 중복 기억 검색을 조사 | 결과를 바꿀 위험이 가장 낮은 **중복 검색 embedding 재사용**을 우선 선정 |
| 3차: 재사용 기능 구현 | 기존 cache를 기억 검색 질문에도 연결하고 ON/OFF 비교 | 20명 × 32 ticks demo에서 검색 계산 **193 → 91회, 52.85% 감소**. 행동 결과 동일 |
| 4차: 실제 API 검증 준비 | 검색·입력·행동 비교 도구와 승인·예산·중단 장치 마련 | 비용 없는 검증 통과. 실제 유료 실행은 별도 승인 대기 |

### 왜 중복 검색부터 줄였나?

세 후보를 비교한 결과는 다음과 같습니다.

- **긴 반복 입력(H1):** 행동 요청의 고정 지시문이 5,441자로, 입력 문자량의 약 44.43%였습니다. 다만 API가 반복 입력을 할인할 수 있어 문자 비율만으로 비용 낭비를 판단할 수 없습니다. 추가 측정이 필요합니다.
- **행동 재시도(H2):** 재시도 표시는 28건이었지만, 같은 직원이 같은 tick에서 첫 AI 판단을 넘어 추가 판단한 경우는 1건으로 증가량은 약 0.74%였습니다. 우선순위를 낮췄습니다.
- **중복 검색(H3):** 검색 질문 193개 중 서로 다른 질문은 82개였습니다. 111개, 즉 57.51%가 완전히 같은 질문이어서 계산을 재사용할 여지가 컸습니다.

### 무엇을 재사용하고, 무엇은 계속 새로 계산하나?

예를 들어 “이 업무와 관련된 기억은?”이라는 문장을 같은 embedding 모델로 다시 처리하면, 이전 숫자 목록을 재사용합니다. 하지만 직원의 기억은 계속 추가되므로 **현재 기억들과의 비교·순위 결정은 매번 새로 합니다.**

검색 결과 자체를 저장해서 재사용하지 않습니다. 검색 문장, 선택할 기억 수, 점수 계산, AI 입력, 행동·대화 정책도 바꾸지 않았습니다. 기억을 삭제하거나 대화를 줄이는 방식의 최적화는 하지 않았습니다.

### 확인한 절감과 그 한계

3차의 기존 병렬 설정에서는 검색 계산이 193 → 91회로 줄었습니다. 전체 embedding 대상 문장은 **904 → 802개**였고, 텍스트를 생성하는 LLM 호출은 **255 → 255회**로 유지됐습니다.

따라서 **“전체 토큰이나 전체 비용이 52.85% 줄었다”는 뜻은 아닙니다.** 같은 질문이 동시에 처음 들어오면 여러 번 계산할 수 있어 절감률도 실행마다 조금 달라집니다. 순차 실행에서는 검색 계산 193 → 82회를 확인했습니다.

Demo의 행동 기록, 선택 기억, 업무 진행, 대화, 관계, stress, AI 입력과 최종 상태가 동일했습니다. 실제 API에서도 같은지 확인하는 것은 다음 단계입니다.

## 2. 실제 AI 검증은 어떻게 할 예정인가?

실제 AI는 같은 입력에도 다른 답을 만들 수 있습니다. 단순히 두 번 실행해서 결과가 달랐다고 cache 때문이라고 판단하면 안 됩니다.

이를 구분하기 위해 **통제 비교 도구**를 준비했습니다.

1. Cache OFF에서 생성 응답과 기억 쓰기 계산 결과를 메모리에 보관합니다.
2. Cache ON에서는 그 응답들을 그대로 재생하고, 검색 embedding만 cache를 거쳐 계산합니다.
3. 숫자 목록, 전체 검색 순위, 선택 기억, AI 입력과 행동 결과를 비교합니다. 입력이 달라지면 재생을 거부하고 실패로 표시합니다.

이 재생은 검증용 장치입니다. 실제 시뮬레이션의 AI 응답을 cache하는 기능으로 도입한 것은 아닙니다. 재생 때문에 ON의 생성 API 비용이 0이 되는 것도 H3의 절감 효과로 계산하지 않습니다.

**추천 pilot:** 같은 설정에서 20명 × 8 ticks(0–7), OFF/ON 통제 비교 1회. 계획상 비용은 약 **$0.05–0.18**, 제안하는 보수적 요청 예약 한도는 **두 조건 합계 $0.50**입니다. 이는 과거 사용량을 이용한 조건부 추정이며 provider의 확정 청구 한도는 아닙니다.

실행 전 사용자 승인과 설정 flag가 모두 필요합니다. 요청 전 예산을 확인하고, 한도에 도달하면 부분 결과를 남기고 중단합니다. 새 유료 API는 이번 세션에서 실행하지 않았습니다.

새 도구의 8-tick demo에서는 검색 59건·AI 입력 79건, 32-tick demo에서는 검색 193건·AI 입력 255건의 동일성 검사를 통과했습니다. 전체 하루의 독립적인 실제 AI 실행 안정성은 아직 모릅니다.

## 3. 기업 갈등 개입: 현재 코드의 의미를 다시 확인

문헌과 기업 사례를 검토하고, 기존 개입 I1·I2·I3가 실제 코드에서 무엇을 하는지 확인했습니다.

| 기존 개입 | 코드에서 확인한 상태 | 해석 |
|---|---|---|
| I1: 관리자 설명 | 설명 실행 표시가 있지만 직원의 입력으로 전달되는 경로가 없음 | 효과를 검증하기 전에 실제 전달 기능이 필요 |
| I2: 마감 조정 | 관리자가 마감 기한을 6 ticks 연장 | 정보를 알려주는 개입보다 업무 조건을 바꾸는 권한 행사에 가까움 |
| I3: 비공개 중재 | 관리자와 직원 1명의 비공개 대화 | 갈등 당사자 둘과 중립 중재자가 참여하는 정식 중재라고 보기 어려움 |

문헌은 조직 차원의 여러 해결 경로, 직접 협의, 공식 절차, 권한 행사를 구분하는 근거로 사용했습니다. 제안한 **개입 시점 × 해결 방식의 3×3 표는 프로젝트용 설계 틀**이며, 문헌에 정해진 단일 공식 모델은 아닙니다.

### 추천 실험: 내용은 같게, 전달 시점만 다르게

먼저 업무 의존성이 막히는 S1 시나리오 하나에서 다음 네 조건을 비교하는 안을 제안했습니다.

- 설명을 하지 않는 조건.
- 같은 역할·업무 설명을 **예방 시점 tick 1**에 전달.
- 같은 설명을 **초기 시점 tick 6**에 전달.
- 같은 설명을 **늦은 시점 tick 8**에 전달.

설명의 내용·발신자·수신자는 같게 유지하고 전달 시점만 바꿉니다. 업무 차단이나 마감 기한을 직접 바꾸지 않습니다. tick 8에 갈등이 이미 발생했다고 보장할 수 없어 “갈등 후” 대신 “늦은 시점”으로 표현했습니다.

핵심 관측값은 **앞 업무가 실제로 끝난 뒤 다음 담당자가 일을 시작하기까지 걸리는 시간**입니다. 업무 완료·차단 시간, 대화·요청, 관계와 stress도 함께 봅니다.

규모는 4조건 × 3개 seed = 12회 실행안입니다. **설계 문서만 작성했으며 개입 기능 구현이나 효과 실험은 하지 않았습니다.** 실제 전달 여부를 먼저 확인하고 비용과 반복 실행 범위를 승인받아야 합니다.

## 4. 검증·산출물·남은 결정

- 최종 전체 테스트: **531개 통과, 1개 skip**. skip은 선택적 실제 CRAFT 통합 테스트입니다.
- 변경 코드의 정적 검사와 diff 검사 통과.
- 이 세션에서 새 유료 API 호출: **0회**. 과거 pilot의 503,945 tokens는 기존 기록을 분석한 것이지 이번에 사용한 양이 아닙니다.
- 코드 변경은 호출 계측, 검색 embedding cache, 검증 도구입니다. 갈등 개입 재설계는 문서만 변경했습니다.

다음 회의에서는 세 가지를 결정하면 됩니다.

1. **H3 실제 API pilot을 승인할지:** 실제 query tokens·비용·검색 동일성을 확인합니다.
2. **갈등 개입의 시점 비교를 주 실험으로 채택할지:** 같은 설명의 내용과 전달 경로를 확정합니다.
3. **전체 하루 검증과 연구 반복을 언제 할지:** 초기 pilot 결과와 실제 비용을 보고 범위를 정합니다.
