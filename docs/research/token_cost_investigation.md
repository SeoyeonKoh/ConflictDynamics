## 1. decide 캐시 적중률이 ~30%에 머문 이유

1. **회고 호출 두 종류(입력의 24%)는 구조상 적중률이 0이다.** system 문구가 0.4~1.0k 글자라 고정 prefix가 1,024토큰에 못 미친다. 나머지는 매번 다른 기억 목록이다.
2. **act는 이미 상한에 가깝다.** 호출당 적중 중앙값은 3,228토큰으로, system(Tier 1+2+3) 크기와 같다. 매 틱 바뀌는 prompt와 schema가 약 절반이라 적중률 상한이 50% 남짓이다. 191건 중 22건은 0 적중이었다.
3. **plan_day는 콜드 캐시 버스트 때문이다.** 48건 중 32건이 0 적중이다. tick 0과 하루 시작 때 10명이 동시에 호출해서 캐시가 아직 쓰이지 않은 상태로 요청이 몰린다. plan schema도 계획마다 달라진다(schema 크기 46종).
4. **`prompt_cache_key`는 이 모델에서 효과가 거의 없다.**
   - GPT-5.6 이후 모델은 캐시 라우팅을 자동으로 하고, 키는 계정별 회계 분리용이라고 문서에 적혀 있다.
   - 시나리오 단위냐 에이전트 단위냐는 적중률에 큰 차이를 내지 않는다.
   - 대신 키 하나에 분당 15건을 넘기면 overflow 라우팅될 수 있다는 경고는 구형 모델 기준이다.
5. **보존 기간.** luna 세대는 `prompt_cache_options.ttl`을 쓴다. 기본 30m(쓰기 1.25×), 12h(쓰기 2.5×, Responses 전용)다. 하루 실행이 30분 안팎이라 기본값으로 충분하다. 12h는 같은 prefix로 여러 replicate를 몇 시간에 걸쳐 돌릴 때만 이득이다.
6. **schema.** 공식 가이드는 schema·tools가 prefix의 일부이므로 안정적으로 유지하라고 권한다. act·plan schema는 고를 수 있는 사람·업무를 enum으로 매 틱 다시 만든다. 다만 관측된 적중량이 system 크기와 같아서, 실제 손실은 "schema까지 캐시되지 못하는 정도(~1k 토큰/호출)"로 보인다. 검증이 필요하다.

## 2. 가장 큰 발견: 기억 프롬프트의 ASCII 이스케이프

- `src/conflict_sim/agent/memory.py:292`의 `MemoryStore._ask`가 `json.dumps(...)`를 `ensure_ascii=False` 없이 호출한다. 그래서 한국어 기억이 모두 `\uXXXX` 형태로 전송된다.
- 다른 프롬프트 경로(agent.py `_complete`)는 `ensure_ascii=False`를 쓰고 있어 이 한 곳만 해당한다.
- 실제 memory.sqlite에서 HDS-005의 기록 40건으로 o200k 토크나이저로 측정했다.
  - 이스케이프 시: 17,437자, **8,804토큰**
  - 이스케이프 없이: 8,212자, **3,735토큰**
  - 2.36배 차이다.
- 이스케이프를 없앤 3,735토큰 중에서도 설명 본문은 1,857토큰뿐이다. 나머지 절반이 id·키 이름·valence·subjects 같은 구조 비용이다.
- 영향 범위는 reflection, end_of_day_reflection, 회고 질문 생성처럼 `MemoryStore._ask`를 거치는 호출 전부다. 입력의 약 24%이며, 회당 약 0.57M 토큰 중 약 0.33M을 줄일 수 있다.
- 비용과 별개로 품질 문제이기도 하다. 모델이 한국어 기억을 이스케이프 코드로 읽고 있다.

## 3. OpenAI 기능별 검토

- **Flex (`service_tier="flex"`).** 같은 모델을 50% 가격에 쓴다. 대신 지연이 늘고 가끔 `429 Resource Unavailable`이 오는데, 이때는 과금되지 않는다. luna 모델 페이지에 "Batch and Flex are priced at 50%"라고 적혀 있지만, flex가 luna를 지원하는지는 가격 페이지에서 한 번 더 확인해야 한다.
  - 실험(비라이브) 실행에 적합하다. 출력이 같은 모델이라 연구 타당도 영향이 없다.
  - 구현: 429면 기존 대기·재시도 경로를 쓰고, 계속 실패하면 `auto`로 대체한다. 클라이언트 타임아웃은 약 15분으로 늘린다.
- **Batch API.** 50% 할인이지만 틱마다 앞 틱 결과에 의존해서 엔진 루프에는 맞지 않는다. 응답이 최대 24시간 걸린다. 여러 replicate를 lock-step으로 묶어도 틱마다 batch를 왕복해야 해서 실행 시간이 시간 단위로 늘어난다.
  - 사후 분석, 인터뷰 일괄 실행, LLM 판정 평가처럼 오프라인 작업에만 권장한다.
- **캐시 쓰기 할증 회피 (explicit 모드).** GPT-5.6 이후 기본 implicit 모드는 마지막 메시지 끝에 breakpoint를 둔다. 그래서 적중하지 않은 입력이 쓰기가(1.25×)로 청구되는 것으로 읽힌다. 문서가 모든 요청이 쓰기인지 명시하지는 않으므로 실측 확인이 필요하다.
  - 다시 쓰이지 않을 부분에는 1.25×를 낼 이유가 없다. 해당하는 것은 회고 전체, act/plan의 동적 prompt, deliverable이다.
  - `prompt_cache_options.mode="explicit"`로 system 끝에만 breakpoint를 두면 그 뒤는 "uncached rate without a cache-write charge"로 청구된다.
  - 효과: 적중하지 않은 입력 약 1.5M × 0.025$/M ≈ 회당 $0.03~0.04, 비용의 약 15%다(할증이 실제로 붙는 경우).
  - 먼저 할 일: usage 응답에 캐시 쓰기 토큰 필드가 있으면 `OpenAIBackend.usage`에 기록한다. 현재는 cached만 기록하고 있다.
- **prewarm (`prompt_cache_options.prewarm`).** 하루 시작 버스트 전에 Tier 1+head prefix를 한 번 써 둔다. 그러면 plan_day와 tick 0 act의 콜드 미스(plan_day 32/48)가 줄어든다. 효과는 작다(입력 약 3~4%).
- **모델 티어링.** luna는 이미 최저가 계열이고 reasoning이 none이라, 호출 유형별로 더 싼 모델로 나눌 여지가 거의 없다.
  - 회고·deliverable만 다른 모델로 바꾸면 연구 비교성(같은 행위자 모델)을 해친다.
- **reasoning_effort·verbosity.** 이미 none이다. 출력은 act 호출당 ~150토큰, 회고 ~280~470토큰이다. verbosity는 luna 페이지에 언급이 없다. `max_tokens_decide=2048`은 상한일 뿐 비용을 만들지 않는다.
- **임베딩.** 회당 약 0.1M 토큰, $0.002로 무시할 수준이다. local_embed로 바꿀 비용상 이유가 없다. 바꾸면 조건 간 측정이 달라지는 위험만 생긴다.
- **Responses API와 previous_response_id.** 이 엔진은 에이전트마다 매 호출을 새로 조립하는 단발 호출 구조다. 대화 상태 체이닝으로 얻을 이득이 작다. 12h ttl을 쓰려면 Responses가 필요하지만, 위 5번대로 필요성이 낮다.

## 4. 프롬프트·엔진 단의 낭비

1. 기억 행의 구조 비용이 크다. id, type, valence, subjects 키 반복이 행당 약 47토큰으로 본문과 비슷하다. 한 줄 서술형(`t12 · 리뷰 대기 중 … (−0.3, 정태우)`)으로 바꾸면 이스케이프 수정 뒤 남은 분량의 30~45%를 더 줄일 수 있다. 다만 evidence id가 필요한 응답에는 짧은 id를 남겨야 한다.
2. end_of_day_reflection의 `plan`(평균 2.9k자)과 `DAY_REVIEW_RECORDS=40`이 크다. 상위 20~25건으로 줄이면 품질 영향이 작을 것으로 예상하지만 프로브로 확인해야 한다.
3. reflection 30회(scoped 기준) 각각 records 약 10.5k자다. 회고 주기나 window(`reflect_window`) 조정은 기억 동역학을 바꾸므로 연구 변수다. 비용 목적으로 건드리지 않기를 권한다.
4. act schema enum과 plan schema가 매 틱 재생성된다. 고정 schema(문자열 필드)에 서버 쪽 검증으로 바꾸면 schema(~1k토큰)까지 prefix에 포함될 수 있다. 검증 재시도가 늘 수 있어 실험이 필요하다.
5. act 호출은 에이전트·틱 약 340칸 중 191~217회다. 계획대로 따를 때는 이미 모델을 생략하고 있다. 더 줄이면 행동 다양성과 rest 측정이 바뀌므로 우선순위가 낮다.

## 5. 우선순위 표

| 순위 | 항목 | 예상 절감(토큰/비용) | 난이도 | 품질·타당도 영향 |
|---|---|---|---|---|
| 1 | memory.py `ensure_ascii=False` | 입력 −14%(회당 ~0.33M), 비용 −12~15% | 1줄 | 긍정(모델이 한국어를 직접 읽음). 단 회고 출력이 달라질 수 있어 이후 실행과 이전 실행은 따로 비교해야 함 |
| 2 | Flex 처리(실험 실행 한정) | 비용 −50%(토큰 동일) | 낮음~중간(429 대체 경로, 타임아웃) | 없음(같은 모델). 실행 시간 증가 |
| 3 | 캐시 쓰기 할증 확인 후 explicit breakpoint | 비용 최대 −15% | 중간(usage 필드 확인·기록, 요청 옵션) | 없음 |
| 4 | 기억 행 압축(서술형 한 줄) | 회고 입력 추가 −30~45%(전체 −4~6%) | 중간 | 중립~경미(evidence id 유지 필요). 프로브 검증 필요 |
| 5 | 하루 회고 기록 40→25건, plan 요약 | 전체 입력 −3~4% | 낮음 | 경미, 프로브 확인 |
| 6 | 하루 시작 prewarm 또는 첫 호출 직렬화 | 전체 입력 −3~4% | 낮음 | 없음 |
| 7 | 고정 act/plan schema + 서버 검증 | act·plan 입력 −10~15%(전체 −6~9%) | 중간~높음 | 재시도 증가 위험 |
| 8 | Batch API(오프라인 평가·인터뷰만) | 해당 작업 −50% | 중간 | 없음. 시뮬레이션 루프에는 부적합 |
| — | prompt_cache_key 변경, 12h ttl, Responses 이전, 임베딩 교체, 모델 티어링 | ≈0 | — | 권장하지 않음 |

1~3을 함께 적용하면 회당 비용이 대략 $0.21~0.29에서 $0.08~0.11 수준(약 −55~60%)으로 내려갈 것으로 추정한다. 1은 토큰 감축, 2는 단가 절반, 3은 할증 제거다.

## 확인 필요

- 회당 $0.15 보고값과 정가 추정 $0.21~0.29의 차이. OpenAI 청구 대시보드나 usage 응답의 cache-write 필드로 확인해야 한다.
- Flex의 gpt-6-luna 지원 여부. 가격 페이지 `?latest-pricing=flex`에서 확인해야 한다.
- implicit 모드에서 적중하지 않은 입력에 실제로 1.25× 쓰기가가 붙는지.
