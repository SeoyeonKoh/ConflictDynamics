# viz 메인 화면 + 통합 백엔드 설계

2026-11-03 · 대상: `viz/`(Vite + TypeScript + Phaser 3), `src/conflict_sim/`

## 1. 의도

Streamlit 대시보드(`src/conflict_sim/dashboard.py`)는 폐기한다. 앞으로 모든 UI는 viz 프론트엔드에 만든다.
지금 viz는 파일을 읽어 리플레이하는 화면과, CLI로 따로 띄운 run에 웹소켓으로 붙는 라이브 화면뿐이다.
run 목록과 run 실행은 Streamlit이 맡고 있고, viz의 run 목록은 vite 개발 서버 미들웨어에만 있다.

이번 작업은 두 가지를 한 번에 한다.

1. **통합 백엔드**: Streamlit이 하던 일(run 목록, 실행, 설정)을 엔진 패키지 안의 Python 서버로 옮긴다.
2. **메인 화면**: viz에 게임 시작 화면 같은 첫 화면을 만든다. 여기서 라이브 실행과 리플레이를 고르고, 환경 설정을 바꾼다.

이 백엔드는 다음 작업(사후 에이전트 인터뷰, 시나리오 생성 에이전트)의 기반이다. 두 기능 모두 엔진의 Python 코드가 필요하므로(에이전트 기억 sqlite, 프롬프트, LLM 백엔드, 시나리오 검증기), 서버를 처음부터 엔진 패키지 안에 둔다.

## 2. 목표 / 비목표 / 반목표

**목표**
- `/`를 열면 메인 화면이 나온다. 버튼은 세로로 **라이브 실행 · 리플레이 · 시나리오 생성(준비 중)**, 그 아래 작은 **환경 설정**이 있다.
- 리플레이: run 목록에서 고르면 리플레이가 열린다. vite 개발 서버 없이도 동작한다.
- 라이브 실행: 시나리오·일수·토큰 상한(무제한 포함)을 고르고 시작하면 라이브 화면으로 넘어간다.
- 라이브 run은 브라우저와 무관하게 서버에서 계속 돈다. 메인 화면에서 진행 중 run에 다시 붙을 수 있다.
- 라이브 화면에서 run을 정지할 수 있고, 정지된 run은 나중에 이어 돌릴 수 있다. 어느 틱에서 멈췄든(정지·토큰 상한·오류·프로세스 종료) 그다음 틱부터 이어 간다(5.3의 응답 기록 재생).
- 환경 설정: UI 언어(한국어/English), 테마(라이트/다크/시스템), AI provider(OpenAI·Demo 연결, 나머지는 자리만).
- 리플레이와 라이브 모두에서 에이전트 간 대화를 대화 단위로 처음부터 끝까지 볼 수 있다. 대사마다 그 말을 하기 전의 속마음을 토글로 펼친다.
- viz 전체 글꼴은 Pretendard (이미 적용됨, 아래 7절).

**비목표 (이번에 안 함)**
- 사후 에이전트 인터뷰 — 다음 작업.
- 시나리오 생성 에이전트 — 버튼만 "준비 중"으로 둔다.
- Anthropic·Google·로컬 provider의 실제 연결 — 선택지는 보이되 비활성.
- 원격 배포, 로그인, 여러 사용자. 이 도구는 로컬 1인용이다(127.0.0.1에만 바인딩).
- Streamlit 코드 삭제 — 새 화면이 대체한 뒤 따로 한다. 이번에는 건드리지 않는다(공용 함수를 옮길 때 import만 맞춘다).
- 기존 리플레이·라이브 화면(HUD, 패널, 맵)의 기능 변경. 예외: 대화 탭 추가, 상단 바의 메인으로·정지 버튼, 고정 문구 번역, 다크 테마.
- 회의 발언의 속마음 기록 추가(회의 프롬프트를 바꾸면 시뮬레이션 동작이 바뀐다). 말하지 않기로 한 판단과 그 이유 표시.

**반목표 (동작해도 실패로 본다)**
- 사용자가 비용을 확인하지 않았는데 유료 API run이 시작된다.
- 브라우저 탭을 닫으면 run이 죽는다.
- 시뮬레이션 동작이 바뀐다. 엔진 수정은 실행 옵션(모델 지정, 무제한 상한, 라이브 속도, 정지), 응답 기록·재생, 라이브 스트림의 속마음 전달에 한정하고, 데모 동작 해시 고정 테스트(`tests/test_retrieval_cache.py`, `tests/test_token_hypothesis_analysis.py`)가 그대로 통과해야 한다.
- API 키가 브라우저로 전송되거나 브라우저에 저장된다.

## 3. 제약

- 새 Python 의존성 없이 만든다. HTTP는 표준 라이브러리(`http.server`의 `ThreadingHTTPServer`), 웹소켓은 이미 쓰는 `websockets`.
- 유료 실행 보호 장치는 유지한다. 엔진은 `ALLOW_PAID_API_EXPERIMENTS=1`과 `--pilot` 없이는 OpenAI run을 거부한다(`experiment.run_scenario`). 서버는 화면에서 비용 확인을 받은 요청에 대해서만 자식 프로세스 환경에 이 값을 넣는다. 서버 자체 환경에는 넣지 않는다.
- API 키는 지금처럼 서버의 `.env`(python-dotenv)에서만 읽는다.
- 저장소 스타일: 최소한의 코드, 기존 패턴 재사용(AGENT.md). 테스트는 pytest, 린트는 ruff, viz는 `npm run check`(tsc).
- 커밋에 AI attribution을 넣지 않는다(저장소 규칙).

## 4. 결정된 사항 (사용자 결정)

- 화면 흐름과 구성은 아래 목업 그대로. 목업: `docs/superpowers/specs/2026-11-03-viz-main-menu/`
  - `main-menu.html` — 세로 버튼 3개 + 환경 설정. 배경은 원근 사무실 바닥 + 실제 캐릭터 스프라이트(`viz/public/assets/characters-v4`), 말풍선이 떴다 사라진다.
  - `settings.html` — 메인 위 모달. 언어·테마 세그먼트, provider 카드 5개(OpenAI·Demo 활성, Anthropic·Google·로컬 "준비 중"), OpenAI 선택 시 API 키 상태(".env에서 읽음", 가려진 값)·판단 모델·대화 모델·임베딩 모델·기본 토큰 상한, Demo 선택 시 안내 문구.
  - `replay-picker.html` — run 목록 모달. 검색창, 시나리오 필터 칩, 표(run 이름+시나리오 · 상태 완료/중단 · 길이 "N일 · M틱" · 모델 · 토큰 · 날짜), 최근순, 행 선택 → "리플레이 열기".
  - `live-setup.html` — 실행 설정 모달. 왼쪽: 시나리오 이름 검색 + 시나리오 카드(이름, 연구 질문, 상속 원본). 오른쪽: 일수 −/+(기본값=시나리오 일수), 토큰 상한 입력 + "상한/무제한" 전환, 예상 사용량, 현재 provider와 "환경 설정에서 변경" 링크, "실행 시작".
- 리플레이는 run 목록에서 고른다.
- 라이브 실행에서 고르는 것: 시나리오, 일수, 토큰 상한(무제한 버튼 포함).
- 시나리오는 이름으로 검색한다(연구 질문은 검색하지 않음).
- 라이브 run은 서버에서 계속 돌고 나중에 다시 들어와 볼 수 있다.
- provider는 자리만 만들고 실제 연결은 OpenAI와 Demo만.
- 서버는 엔진 패키지 안에 두고, run은 별도 프로세스로 띄운다(아래 5절, 방식 A).
- 글꼴은 Pretendard.
- 어느 틱에서 멈췄든 이어 가기를 이번 범위에 넣는다. 방식은 응답 기록 재생(5.3).
- 대화 세부 보기를 리플레이·라이브 모두에 넣는다. 속마음은 토글. 목업: `conversation.html` — 오른쪽 패널의 새 "대화" 탭. 왼쪽 대화 목록(종류 대화/회의/메시지, 시작 시각 "N일차 HH:MM", 참여자, 장소, 대사 수), 오른쪽 선택한 대화(제목 = 종류·장소, 시간 범위, 참여자; 대사마다 이름·직책·시각·말풍선, 그 아래 "💭 속마음" 접힘), 위쪽 "속마음 모두 펼치기" 스위치. 회의 발언은 "회의 발언은 속마음 기록이 없어요".

## 5. 구조

```
브라우저 (viz)
  ├─ HTTP  → conflict-server (127.0.0.1:<api port>)   목록·시나리오·설정·실행/정지·run 파일
  └─ WS    → 각 라이브 run 프로세스의 Stream (127.0.0.1:<run port>)   기존 라이브 프로토콜 그대로

conflict-server  ──spawn──▶  conflict-company-experiment <scenario> --live-port 0 ...  (run마다 1 프로세스)
```

### 5.1 서버 (`src/conflict_sim/server.py`, 진입점 `conflict-server`)

엔진 함수를 직접 불러서 처리한다. run 자체는 돌리지 않는다.

| API | 하는 일 | 쓰는 엔진 코드 |
|---|---|---|
| `GET /api/runs` | run 목록. 진행 중이면 `live: true`와 연결 정보 포함 | `discover_company_runs` (dashboard.py에서 공용 모듈로 이동) |
| `GET /runs/<path>/<file>.jsonl` | run 파일 제공 (`frames`, `events`, `inspect`). 지금 vite 미들웨어와 같은 경로·규칙이라 `replay.ts`는 그대로 | — |
| `GET /api/scenarios` | 이름, 연구 질문, 상속 원본, 기본 일수, 예상 호출 수, 같은 시나리오의 지난 run 하루 토큰 | `experiment.SCENARIOS`, `load_c15_scenario`, `build_company_config`, `estimate_calls` |
| `POST /api/live` | run 시작. 본문: 시나리오, 일수, 토큰 상한 또는 무제한, 비용 확인 여부 | 자식 프로세스 실행 |
| `GET /api/live` | 진행 중 run 목록: 시나리오, run 폴더, WS 포트, 현재 일차·시각, 상태 | `frames.jsonl` 끝부분 |
| `POST /api/live/<id>/stop` | 정지 → 일시정지 저장 | 자식에 SIGTERM |
| `POST /api/runs/<path>/resume` | 중단된 run 이어 돌리기 (라이브로) | `--resume` |
| `GET/PUT /api/settings` | provider, 세 모델, 기본 토큰 상한. 응답에 "OpenAI 키 있음" 여부만 포함 | `.env` 확인 |

- 개발 모드: vite는 그대로 화면을 띄우고 `/api`와 `/runs`를 서버로 프록시한다. 기존 `vite.config.ts`의 `/runs` 미들웨어는 지운다.
- 배포 모드: 서버가 `viz/dist`(빌드 결과)를 정적 파일로도 제공한다. `conflict-server` 하나로 끝.
- 서버 재시작: run 프로세스는 서버와 분리해 띄운다(새 세션). 서버가 다시 뜨면 run 폴더의 기록 파일(5.2)을 보고 살아 있는 run을 다시 찾는다.

### 5.2 라이브 run 프로세스

- 기존 CLI를 그대로 쓴다: `conflict-company-experiment <scenario> --backend openai|demo --pilot --days N [--max-total-tokens N] --live-port 0 --output-root <dir>`.
- `--live-port 0`이면 OS가 빈 포트를 준다(`Stream.start`가 실제 포트를 돌려줌). CLI가 이미 `Viewer WebSocket: ws://127.0.0.1:<port>`를 출력한다.
- 서버는 run 폴더에 진행 기록 파일(예: `live.json`: pid, 포트, 시작 시각, 시나리오, 설정)을 남긴다. 목록·재접속·재시작 후 복구는 이 파일과 pid 생존 여부로 판단한다.
- run 폴더 위치는 `runs/` 아래(리플레이 목록에 자동으로 잡히도록). 기존 run 구조(`<root>/<scenario>/replicate-1/`)를 따른다.
- 진행 중인 run의 `frames.jsonl`은 계속 쓰여지므로, 라이브로 붙지 않고 리플레이로 열어 지금까지를 볼 수도 있다(추가 작업 없음).

### 5.3 엔진 수정 (실행 옵션만, 동작 불변)

1. **모델 지정**: `conflict-company-experiment`에 판단·대화·임베딩 모델 옵션을 추가한다. 지금은 `company_runtime.build_company_config`에 `gpt-6-luna` / `text-embedding-3-small`이 고정돼 있다. 옵션을 안 주면 지금과 같다.
2. **무제한 토큰 상한**: 상한 없음을 표현할 수 있게 한다(`Config.max_total_tokens`는 지금 `ge=1` 정수, OpenAI 기본 500k). CLI에서 명시적인 값(예: `--max-total-tokens 0` 또는 별도 플래그)으로 상한 검사를 끈다. 주의: 상한은 지금 **segment마다** 적용된다(resume하면 새로 센다, 2026-11-03 r10_midweek v3에서 확인). 화면 문구는 "이번 실행 기준"으로 쓴다.
3. **라이브 속도 (설계자 결정)**: `run_scenario`는 `Stream`을 `delay=0`으로 만든다. Demo는 하루 run이 1초 안에 끝나서 화면에 틱이 보이기도 전에 프로세스가 끝난다(builder check에서 실측 0.77초). 틱 간격 옵션을 추가한다. Demo 기본값 1틱/초, 기존 속도 조절(`speed`)이 이 간격에 곱해진다. OpenAI는 기본 0(LLM 응답 시간이 이미 속도를 정한다). 시뮬레이션 동작은 바뀌지 않는다.
4. **정지**: SIGTERM을 받으면 진행 중인 틱을 끝낸 뒤 토큰 상한에 닿았을 때와 같은 경로로 일시정지한다(`paused.json`에 마지막으로 끝난 틱 기록, 상태 `paused`, 스트림에 `paused` 상태 전송).
5. **어느 틱에서든 이어 가기 — 응답 기록 재생 (사용자 결정, 이번 범위)**: 목표는 어떤 틱에서 멈췄든(정지, 토큰 상한, 오류, 프로세스 종료) 그다음 틱부터 이어 가는 것.
   - 방식: 매 틱 상태를 파일로 저장하지 않는다. 엔진은 시작 상태 + 난수 시드 + LLM 응답(완성 + 임베딩)이 같으면 같은 상태를 만든다. 병렬 판단도 결과를 설정 순서대로 적용하므로 결정적이다(두 번째 builder check: `PYTHONHASHSEED`를 바꿔도 Demo events 동일). 그래서 **모든 LLM 응답을 기록**하고, 이어 갈 때 엔진을 다시 돌리며 멈춘 지점까지는 기록된 응답을 넣는다. 그 뒤로는 실제 backend로 바꾼다. 패턴은 `probe.Switch`와 같다.
   - **재생은 항상 run 시작(틱 0)부터 (설계자 결정)**. 하루 끝 체크포인트에서 시작하지 않는다. 체크포인트는 `Loop.meeting_notes`와 `Agent`의 `_view`·`_place`·`_recalled`를 빠뜨리고, 새 `Frames`는 차이 계산 상태가 비어 있어서, 체크포인트에서 되살린 run은 프롬프트와 frames가 원래 run과 달라진다(실측: r10_enterprise_weekly 2일차 283개 중 16개, p0_documents_ko 333개 중 6개 프롬프트 불일치; 첫 frame에 task 62개). 틱 0부터 재생하면 엔진·체크포인트를 고치지 않고도 정확하다. 비용은 CPU뿐(API 호출 없음).
   - 재생은 run 폴더의 파생 파일(`events.jsonl`, `frames.jsonl`, `inspect.jsonl`, `memory.sqlite`, 체크포인트 등)을 처음부터 다시 만든다. 응답 기록이 원본이다. 재생 중에는 라이브 화면에 진행률만 보여 주고, 재생이 끝난 틱부터 평소처럼 스트림한다.
   - **기록 내용**: run 폴더에 응답 기록 파일을 추가한다. 응답을 받는 즉시 append + flush(프로세스가 갑자기 죽어도 남도록).
     - 완성 응답 원문(검증 실패한 응답과 재시도 응답 포함).
     - **임베딩 벡터 전부 (설계자 결정)**: 기억 저장용(`Loop._embed`, 지금은 캐시 없이 항상 실제 API)과 검색 쿼리용 모두. `retrieval_cache.sqlite`로는 부족하다: 기억 저장 임베딩은 캐시되지 않고, 쿼리 캐시는 `insert or replace`라 병렬로 같은 텍스트를 두 번 임베딩하면 실제로 쓰인 벡터가 남는다는 보장이 없으며, 캐시를 끌 수도 있다(`--no-retrieval-cache`). OpenAI 임베딩은 호출마다 비트 단위로 같지 않다. 크기는 float64(원래 run과 비트 단위로 같아야 재생이 정확함)로 하루 수십 MB 수준(`memory.sqlite`가 이미 하루 13MB대).
     - 지금 `llm_audit.jsonl`은 해시·토큰 수만 있고 원문이 없다.
   - 찾기: 판단 호출이 병렬(`Loop._judge`, workers)이라 순서가 아니라 (에이전트, 호출 종류, 프롬프트 해시 또는 임베딩 입력)으로 응답을 찾는다. 같은 키가 여러 번이면 나온 순서대로.
   - **틱 중간에 멈춘 경우 (설계자 결정)**: 멈춘 틱에서 받은 응답은 기록에서 잘라낸다(마지막으로 끝난 틱까지만 남김, `truncate_run`처럼). 멈춘 틱은 실제 backend로 처음부터 다시 돈다. 이유: 검증 실패로 멈춘 틱의 응답을 재사용하면 같은 오류로 다시 멈춘다(`runs/c16-real-r10-midweek-v3-stale`의 tick 65 "Invalid action from HDS-005"가 이 경우). 잃는 것은 그 틱의 호출 몇 개뿐. 잘라내므로 segment가 여러 번 쌓여도 "같은 키는 나온 순서대로"가 꼬이지 않는다.
   - 어긋남: 재생 중 기록에 없는 프롬프트·임베딩 입력이 나오면(엔진 코드가 바뀌었거나 비결정성) 그 자리에서 이어 가기를 멈추고 이유를 알린다. 유료 API로 몰래 넘어가지 않는다.
   - 이 기능 이전의 run(응답 기록 없음)은 지금처럼 하루 끝 체크포인트에서 이어 간다(위의 부정확성은 그대로 남는다는 점을 확인 창에 알림). 체크포인트도 없으면 이어서 실행을 보여 주지 않는다.
   - 재생은 API를 부르지 않으므로 비용이 없다. 긴 run(예: 6일)은 재생에 수십 초~수 분이 걸릴 수 있다.
   - 원하는 틱에서 갈라 새 run으로 돌리기(개입 실험용)는 같은 구조로 가능하지만 **이번 범위가 아니다**.
   - 필수 테스트: (a) 틱 t에서 정지 → 이어 간 run과 (b) 한 번에 끝까지 간 run의 events/frames가 같다. t는 대화가 열려 있는 틱, 회의가 있는 날을 포함한다(회의가 있는 시나리오 사용, 예: `r10_enterprise_weekly` 또는 `p0_documents_ko`).
     - Demo만으로는 부족하다: Demo는 응답이 프롬프트에만 의존하고 임베딩이 해시라서, 기록 없이 다시 돌려도 같아진다. **호출마다 무작위 응답·무작위 임베딩을 내는 테스트용 backend**로 (a)/(b)를 비교해, 기록 재생만이 결과를 같게 만들 수 있는 조건에서 검증한다.
     - 오류로 틱 중간에 멈춘 경우(검증 실패 주입)도 이어 가기가 되는지 테스트한다.

### 5.4 화면 (viz)

- 메인 화면·모달은 HTML/CSS 오버레이로 만든다(Phaser 아님). 기존 `style.css` 토큰과 유리 패널 스타일을 쓴다.
- 화면 이동은 URL로 한다. `/` = 메인, `?replay=<run>` = 리플레이(기존), `?ws=...` = 라이브(기존), `?live=<id>` = 서버가 관리하는 라이브 run(서버에서 포트를 받아 기존 라이브 경로로 붙음). 기존 `main.ts`의 부팅 경로를 그대로 살린다.
- 리플레이·라이브 화면 상단 바에 "메인으로" 버튼을 둔다. 라이브 화면에는 "정지" 버튼을 둔다(기존 일시정지/재개/속도 조절과 별개: 일시정지는 엔진을 잠시 세울 뿐, 정지는 run을 끝내고 저장).
- 메인의 라이브 실행 카드에 진행 중 run을 보여 준다(예: "진행 중 1개 · r10_midweek 2일차 11:30"). 누르면 그 run에 붙는다. 여러 개면 목록으로.
- 리플레이 목록에서 상태가 "중단"인 run은 "이어서 실행"을 고를 수 있다(5.1 resume).
- 이어서 실행 (설계자 결정): 원래 run의 backend·모델·일수를 `resolved_config.json`에서 그대로 쓴다(지금 환경 설정 값이 아님). 작은 확인 창에서 이번 segment의 토큰 상한(기본값 = 환경 설정의 기본 상한, 무제한 가능)을 고르고, OpenAI면 비용 확인을 거친다. 상한은 segment마다 새로 센다. 엔진은 resume 때 상한을 안 주면 500k로 돌아가므로 서버가 항상 명시해서 넘긴다.
- 실행 시작 확인:
  - OpenAI: 예상 사용량과 상한을 보여 주는 확인 창을 거쳐야 시작된다. 무제한이면 경고 문구를 더한다. 확인 결과를 `POST /api/live`에 함께 보낸다.
  - Demo: 확인 창 없이 바로 시작.
- 예상 사용량: 같은 시나리오의 지난 run이 있으면 하루 토큰 × 일수, 없으면 `estimate_calls`의 호출 수만 보여 준다.

### 5.5 대화 보기

- 데이터 출처 (2026-11-03 `runs/c16-real-r10-midweek-v3-stale`에서 확인):
  - 대사: `frames.jsonl`의 frame `lines`(`speaker`, `text`, `session`)와 `sessions`(종류, 장소, 참여자).
  - 대화를 연 사람의 속마음: `events.jsonl`의 `action` 이벤트(`kind` talk/message, `payload.reflection`).
  - 답한 사람의 속마음: `events.jsonl`의 `decision` 이벤트(`posted: true`, `payload.reflection`, `utterance_id`).
  - 회의(`meeting:*`) 발언: 속마음 없음(엔진의 회의 발언 호출이 생각을 묻지 않음). 비목표.
- 라이브: 지금 스트림은 `lines`만 보내고 `action`/`decision` 이벤트의 속마음은 보내지 않는다(`frames.py`는 task·rejected·outcome·shock·session 이벤트만 전달). 스트림 형식을 넓혀 대사마다 속마음과 발화 id를 함께 보낸다. 보는 쪽 데이터만 바뀌고 시뮬레이션 동작은 그대로. 새 run의 `frames.jsonl`에도 같이 남는다.
- 리플레이: 새 형식이 있으면 그것을, 없으면(예전 run) `events.jsonl`에서 같은 대화·화자·순서로 찾아 붙인다. 못 찾으면 속마음 토글을 숨긴다.
  - 대화를 연 사람의 `action` 이벤트에는 session id가 없지만 `talk:{tick}:{actor}`로 다시 만들 수 있다. DM은 frames `sessions`에 대개 없지만 id `dm:A:B:day`가 참여자를 말해 준다.
  - 계획을 따라 연 대화는 속마음 칸에 대사 자체가 들어 있다(r10_human-v6에서 64개 중 19개). 속마음이 대사와 같으면 속마음 토글을 숨긴다 (설계자 결정).
- 화면 이름은 시나리오의 `display_name`, 직책은 `title`(`resolved_config.json`의 agents). 기존 HUD처럼 id(HDS-001)를 그대로 보여 주지 않는다.
- 시각 표시는 기존 HUD의 일차·시각 표기를 따른다. 대화를 누르면 지도에서 그 시각으로 이동할지는 빌더가 정한다(리플레이에서만 의미 있음).
- 기존 Events 탭은 그대로 둔다.

### 5.6 설정 저장

| 항목 | 저장 위치 |
|---|---|
| UI 언어, 테마 | 브라우저 localStorage (기기마다) |
| provider, 세 모델, 기본 토큰 상한 | 서버 설정 파일 (저장소 밖 커밋 안 되는 위치) |
| API 키 | `.env`만. 화면은 "있음/없음"만 안다 |

- 다크 테마: viz의 색 토큰(`:root`) 전체에 다크 값을 정의한다. 대상은 패널·메뉴·HUD 등 UI 크롬이다. 사무실 맵·캐릭터 그림은 바꾸지 않는다.
- UI 언어: 메인·모달·기존 HUD의 고정 문구(지금 영어: Tasks, Relations, Events 등)를 한/영 사전으로 바꾼다. 에이전트가 만든 내용(대화, 문서, 이름)은 번역하지 않는다. 기본값은 한국어.

## 6. 성공 기준

1. `conflict-server` 하나만 띄우고 `/`를 열면 메인 화면이 나온다(빌드된 viz). 개발 모드에서는 `npm run dev` + `conflict-server`.
2. 리플레이 → 목록에서 run 선택 → 리플레이가 열린다. vite 미들웨어 없이.
3. 라이브 실행 → Demo, `r10_midweek`, 1일 → 시작하면 라이브 화면에서 틱이 진행된다.
4. 탭을 닫았다가 `/`를 다시 열면 진행 중 run이 보이고, 눌러서 다시 붙는다.
5. 하루 중간(대화가 열린 틱 포함)에 정지 → 상태가 중단으로 바뀌고 리플레이 목록에서 "이어서 실행"하면 정지한 다음 틱부터 진행된다. Demo에서 정지 없이 끝까지 간 run과 결과가 같다.
6. OpenAI 선택 시 확인 창 없이는 run이 시작되지 않는다(서버도 확인 플래그 없는 요청을 거부한다).
7. 서버를 재시작해도 진행 중 run은 계속 돌고, 다시 목록에 잡힌다.
8. 언어·테마 바꾸면 즉시 반영되고 새로고침 후에도 유지된다.
9. 리플레이(예전 run 포함)와 라이브에서 대화 탭으로 대화 하나를 처음부터 끝까지 읽을 수 있고, 1:1 대화·메시지의 대사마다 속마음이 펼쳐진다. 라이브에서는 진행 중인 대화에 대사가 실시간으로 붙는다.
10. 기존 테스트 전부 통과(동작 해시 고정 포함), ruff, `npm run check` 통과.

## 9. 설계자가 정한 것 (사용자가 확인할 것)

대화 중 사용자가 직접 정하지 않았고 설계자가 정한 것들이다. 다르게 원하면 고친다.

- API 키는 화면에서 입력받지 않고 서버 `.env`만 쓴다.
- 언어·테마는 브라우저에, provider·모델·기본 상한은 서버 설정 파일에 저장한다.
- 화면 이동은 URL로(페이지 새로 열기) 해서 기존 리플레이·라이브 부팅 코드를 살린다.
- OpenAI 실행은 화면의 비용 확인을 승인으로 보고, 그때만 자식 프로세스에 `ALLOW_PAID_API_EXPERIMENTS=1`을 준다. Demo는 확인 없이 시작.
- 다크 테마는 UI 크롬만. 사무실 맵 그림은 그대로.
- UI 언어 기본값 한국어. 에이전트가 만든 내용은 번역하지 않는다.
- Demo 라이브 기본 속도 1틱/초. OpenAI는 추가 지연 없음.
- 이어서 실행은 원래 run의 provider·모델·일수를 쓰고, 토큰 상한만 다시 고른다.
- 메인 라이브 카드에 진행 중 run 표시, 리플레이 목록의 중단 run에 "이어서 실행".
- 재생 중 기록과 어긋나면 유료 API로 넘어가지 않고 멈춘다.
- 대화 탭은 기존 Events 탭 옆에 추가(Events는 그대로).
- 이어 가기 재생은 항상 틱 0부터(하루 끝 체크포인트는 정확하지 않음).
- 응답 기록에 임베딩 벡터까지 넣는다(재생을 완전히 오프라인·정확하게). 하루 수십 MB.
- 틱 중간에 멈추면 그 틱의 응답은 버리고 그 틱을 다시 돈다.
- 계획을 따라 연 대화처럼 속마음이 대사와 같으면 속마음 토글을 숨긴다.
