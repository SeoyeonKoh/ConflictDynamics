# 시나리오 생성기 설계

2026-11-10 · 대상: `src/conflict_sim/`(서버·엔진 설정), `viz/`(메인 메뉴의 "시나리오 생성")
선행 작업: `2026-11-03-viz-main-menu-design.md`(conflict-server, 메뉴), `2026-11-03-agent-interview-design.md`(LLM을 부르는 서버 기능의 선례)
시안: `2026-11-10-scenario-generator/layout.html` — 사용자는 **B안(대화형 한 화면)**을 골랐다.

## 1. 의도

인사팀이나 조직 연구자가 "이런 실험을 하고 싶다"에서 출발해, 시뮬레이터가 그대로 실행할 수 있는 시나리오를 얻는다. 사용자가 든 실험의 예는 세 가지다.

- 특정한 조직 구조가 업무 효율에 미치는 영향
- 특정 업무가 스트레스에 미치는 영향
- 특정한 성향의 에이전트가 집단에 미치는 영향 (예: 부적절한 언어로 피드백해 상대를 기분 나쁘게 하는 사람)

이 사람들은 YAML이나 엔진 구조를 모른다. 원하는 조직 구조를 말로 설명하고, 가지고 있는 업무 자료(md 파일)를 주면, 도구가 그 자료를 바탕으로 가상의 일을 만들어 사람들에게 배정한 시나리오를 써 준다. 효과를 보려면 비교 대상이 필요하므로, baseline과 비교군을 짝으로 만들 수 있어야 한다.

## 2. 목표 / 비목표 / 반목표

**목표** (모두 사용자 결정)
- 두 모드:
  - **처음부터 만들기**: 실험 의도 · 조직 구조 설명 · md 자료 → 새 회사와 새 시나리오.
  - **기존 시나리오에서 변형**: 기존 시나리오를 고르고 바꿀 요인을 말하면, 그 요인만 바꾼 비교용 시나리오. 원본이 baseline이 된다.
- 처음부터 만들 때 **baseline과 비교군을 짝으로 생성**하는 선택지.
- 검토 두 겹:
  - **기계 검토**: 형식에 안 맞으면(엔진 검증 실패) AI에게 자동으로 수정을 요청한다.
  - **사람 검토**: 사람이 미리보기를 보고 자연어로 수정을 지시한다.
- 화면은 **대화 + 미리보기 한 화면**(B안). 의도·조직·자료도 대화창에 말하고 파일을 붙인다. 빠진 게 있으면 AI가 되묻는다.
- 저장하면 라이브 실행 목록에 나타나 바로 실행할 수 있다.

**비목표** (사용자 결정: 이번 범위는 저장까지)
- 실험 결과 비교, run · 실험 요약, 분석 AI 어시스턴트 — 다음 계획으로 기록해 두었다(§9).
- 시나리오를 실행하는 것 자체(이미 있는 라이브 실행이 맡는다).
- 맵(사무실 배치) 생성. 지금 사무실 맵을 그대로 쓴다.

**반목표**
- 비교군이 의도한 요인 말고도 다른 곳이 조용히 달라진다. (실험이 무효가 된다)
- 기존 시나리오나 프리셋 파일을 덮어쓰거나 고친다. 변형은 언제나 새 파일이다.
- 사용자가 모르는 사이에 유료 호출이 나간다. (Demo 설정에서는 생성하지 않는다)
- 검증을 통과하지 못한 시나리오가 라이브 목록에 나타난다.

## 3. 제약

- 새 Python 의존성 없음(인터뷰와 같은 원칙). conflict-server에 API를 더하고 같은 보안 규칙(로컬 Host/Origin, JSON 본문, 키는 브라우저로 가지 않음)을 따른다.
- 생성 AI는 환경 설정의 OpenAI 모델을 쓴다. 인터뷰에서 확인한 대로 그 run 설정의 `reasoning_effort`(없으면 `"none"`)를 함께 보낸다(gpt-6 모델은 temperature를 추론 off에서만 받는다).
- 사무실 맵 자리가 20석이라 한 시나리오는 **3~20명**(§4.1).
- 시나리오의 "올바름"은 엔진이 정한다: `build_company_config(<시나리오>)`가 예외 없이 끝나야 하고, 회사 프리셋은 `conflict-company-validate`를 통과해야 한다. 생성기는 검증을 따로 만들지 않고 엔진 검증을 그대로 부른다. 생성된 회사에 적용되는 느슨한 규칙(§4.1)도 엔진 검증 안에 둔다.
- 기존 회사 프리셋과 기존 시나리오의 동작은 바뀌지 않는다. 기존 테스트가 그대로 통과해야 한다.
- 시나리오 글쓰기 규칙은 `docs/scenario-writing-guide.md`가 정한다(실 API 실험으로 확인한 지침). 생성 AI는 이 지침을 따라 써야 한다.

## 4. 시나리오는 무엇으로 이루어지나 (엔진에서 확인한 사실)

시나리오 하나는 여러 조각이다. 생성기가 만들어야 하는 것도 이 전부다.

| 조각 | 지금 있는 곳 | 내용 |
| --- | --- | --- |
| 회사 프리셋 | `conf/company/<preset>.yaml` | 페르소나 · 조직 · 사무실 파일을 묶는다 |
| 페르소나 | `conf/personas/<preset>.yaml` | 사람마다 이름, 부서, 역할, `reports_to`, 권한(assign/approve/reject/evaluate), 기술, DISC, 그리고 서술형 성향: `communication_style`, `pressure_response`, `conflict_engagement_style`, `personal_work_priority`, `initial_relationship_notes` 등 |
| 조직 | `conf/environment/org/<preset>.yaml` | 부서와 핵심 업무 그래프(workflow tasks) |
| 사무실 | `conf/environment/office/*.yaml` | 그대로 재사용 |
| 시나리오 | `conf/scenario/company_c15/<id>.yaml` (`C15Scenario`) | `preset`, `extends`, `research_question`, `manipulated_variable`, `fixed_variables`, `task_runtime`(핵심 업무 공수·마감), `projects`, `extra_tasks`(낮에 들어오는 일 포함), `deliverables`, `materials`, `initial`(진행 상태), `backstory`(각자의 어제까지 사정), `engine.meetings`·`engine.shocks`·`interventions`, `observable_outputs`, `manipulation_check` 등 |

주의할 점:
- 시나리오의 `task_runtime`은 프리셋 조직의 핵심 업무 목록과 정확히 같아야 한다(엔진이 검사한다).
- 페르소나 파일의 `disc_policy`는 DISC를 소통 성향으로만 쓰고 능력·공격성 등을 **DISC에서 추론하지 말라**고 한다. "무례한 피드백" 같은 행동 성향은 DISC로 표현하지 않고 서술형 성향 칸에 명시적으로 적는다. 페르소나 스키마는 이번에 바꾸지 않는다(내 판단; 서술형 칸으로 충분하다).

### 4.1 조직 틀: 기존 회사는 그대로, 생성된 회사는 느슨하게 (사용자 결정)

지금 엔진은 회사 하나의 틀에 묶여 있다(`company.py` 검증, `company_runtime.py`).

| 지금 규칙 | 있는 곳 |
| --- | --- |
| 인원은 정확히 10명 또는 20명, 20명이면 DISC 유형이 각 5명 | `company.py` 검증 |
| 핵심 업무는 정확히 15개, 갈등 사건은 정해진 10개 | `company.py` 검증 |
| 맨 위 보고자는 프로젝트 매니저 한 명 | `company.py` 검증 |
| 결재 단계는 업무 번호 T03~T15에 붙은 고정 표 | `company_runtime.py`의 `TASK_AUTHORITY_SCOPE` |
| 부서 자리는 기존 부서 id 6개에 고정 | 사무실 맵 |

사용자는 세 가지 길(틀 안에서만 / 엔진 전체 일반화 / 섞기) 중 **섞기**를 골랐다.

- **기존 회사**: 위 규칙 그대로. 검증도 동작도 바뀌지 않는다.
- **생성된 회사**: 느슨한 규칙을 적용한다.
  - 인원 **3~20명**. DISC 분포 제한 없음.
  - 핵심 업무 개수 자유(1개 이상). 갈등 사건 개수 자유(0개 가능).
  - 결재 단계는 **회사 파일에 직접 적는다**. 적지 않은 업무는 지금 고정 표를 따른다(표에 없는 번호면 결재 없음).
  - 부서는 **최대 6개**(맵의 부서 자리 수). 부서 id가 맵의 6개와 다르면 빈 부서 자리에 차례로 배정한다.
  - 맨 위 보고자는 한 명(내 판단: 보고 라인이 한 뿌리라는 엔진 가정은 유지한다. 그 사람이 "프로젝트 매니저" 역할일 필요는 없다).
- 어느 회사가 "생성된 회사"인지는 회사 파일에 표시한다(표시 방식은 빌더 판단). 표시가 없는 파일은 기존 규칙으로 검증한다.
- 그 밖의 검증(보고 라인에 순환 없음, 업무 선후 관계의 id가 실제로 있음, 담당자가 실제 사람임 등)은 두 쪽 모두 그대로다.

## 5. 흐름

```text
메인 "시나리오 생성" ─▶ 작업 화면 (왼쪽 대화, 오른쪽 미리보기)
  1. 모드: 처음부터 / 기존에서 변형 (대화로 말하거나 고른다)
  2. 입력: 실험 의도, 조직 구조 설명(또는 바꿀 요인), md 자료 첨부, 짝 생성 여부, 일수
     └ 빠진 것은 AI가 되묻는다
  3. 생성 ─▶ 초안 (baseline [+ 비교군])
  4. 기계 검토: 엔진 검증 ─(실패)▶ 오류를 AI에 돌려주고 자동 수정 ─▶ 다시 검증
     └ 대화창에 한 줄로 기록 ("형식 검사: 오류 3개 → 자동 수정 → 통과")
  5. 사람 검토: 미리보기를 보며 자연어 지시 ─▶ AI가 초안을 고침 ─▶ 4로
  6. 저장 ─▶ 파일 기록 ─▶ 라이브 실행 목록에 나타남
```

### 5.1 작업 화면 (B안, 시안 참고)

- **왼쪽 대화**: AI의 질문·보고, 사용자의 지시, 기계 검토 기록이 한 줄기로 쌓인다. md 파일을 붙일 수 있다.
- **오른쪽 미리보기**: baseline / 비교군 전환, 탭은 **조직도 · 사람·성향 · 업무 · 하루 일정 · 실험 설명 · YAML**.
- 미리보기 아래에 **"비교군과 다른 점"**: 두 버전의 차이를 자동으로 계산해 보여 주고, 의도한 요인 하나뿐이면 ✓, 아니면 경고한다.
- **저장** 버튼은 검증을 통과한 상태에서만 누를 수 있다.

### 5.2 변형할 수 있는 요인 (내 판단으로 시작 범위를 정함)

| 요인 | 예 | 바뀌는 조각 |
| --- | --- | --- |
| 조직 구조 | 결재를 팀장 1명이 쥠 ↔ 리드에게 위임, 팀 구성 | 페르소나의 `reports_to`·권한, 조직 |
| 업무 | 업무량·난이도·마감, 특정 업무 추가 | `task_runtime`, `projects`, `extra_tasks` |
| 성향 | 한 사람을 "부적절한 언어로 피드백하는 사람"으로 | 그 사람의 서술형 성향 칸 |
| 사건 | 하루 중 돌발 상황, 갑작스러운 마감 변경 | `engine.shocks`, 낮에 들어오는 일 |

### 5.3 비교군의 "한 요인만 다름" 확인

파일 배치와 상관없이 확실하게 하려고, 두 시나리오를 각각 `build_company_config`로 **해석한 최종 설정끼리** 비교한다. 다른 곳을 요인별로 분류해 보여 주고, 사용자가 고른 요인 밖의 차이가 있으면 저장 전에 경고한다(저장을 막을지 경고만 할지는 빌더 판단, 기본은 경고 + 확인).

### 5.4 성향을 넣는 규칙 (내 판단)

`docs/scenario-writing-guide.md` §2.1과 `docs/company-world-plan.md`는 "갈등은 성격이 아니라 구조에서 나와야 한다"며 비합리적 성향을 양성 대조군에만 허용한다. 성향 실험은 사용자가 직접 든 목표이므로 다음처럼 맞춘다.

- 비합리적·공격적 행동 성향은 **사용자가 명시적으로 요청한 사람에게만** 넣는다. AI가 스스로 넣지 않는다.
- 그 성향이 비교 요인이 아닌데 들어가면(두 버전 모두에 있는 경우 포함), AI가 "지침과 다르고 결과를 흐릴 수 있다"고 대화창에 알린다. 막지는 않는다.
- 표현은 **행동 묘사**로 쓴다. 예) "피드백할 때 상대를 깎아내리고 비꼬는 말을 쓴다. 잘못을 사람 탓으로 돌린다." 욕설·비하 표현 자체를 페르소나에 적지 않는다.
- "다른 점" 확인(§5.3)에 성향 차이가 그대로 드러난다.

## 6. 실험 정보를 함께 적는다

나중의 결과 비교(§9)가 읽을 수 있도록, 생성기는 시나리오에 다음을 채운다. 기존 칸(`research_question`, `manipulated_variable`, `fixed_variables`, `observable_outputs`, `manipulation_check`)을 우선 쓰고, 부족한 것은 시나리오 형식(`C15Scenario`)에 **선택 칸 `experiment`를 하나 더해** 구조화해 담는다(내 판단; 이 칸이 없는 기존 시나리오는 그대로 읽힌다).

```yaml
experiment:
  id: rude-feedback-01          # 짝을 잇는 실험 id
  role: variant                 # baseline | variant
  factor: disposition           # structure | work | disposition | event
  hypothesis: "무례한 피드백을 받은 상대는 스트레스가 오르고 그 사람을 향한 관계가 음수가 된다."
  measures:
    - metric: stress            # stress | mood | relation | task_completion | rest_ratio
      subject: partners_of:A07  # 누구를 재는가: 사람 id, all, partners_of:<id>
      toward: null              # relation일 때 누구를 향한 값인가
      direction: up             # up | down
    - {metric: relation, subject: partners_of:A07, toward: A07, direction: down}
  behaviour_checks:
    - "A07이 피드백에서 깎아내리거나 비꼬는 말을 실제로 했는가"
```

칸 이름과 값 목록은 예시다. 빌더가 다듬되, 다음 네 가지는 기계가 읽을 수 있어야 한다.

- **가설**: 예) 무례한 피드백을 받은 상대는 스트레스가 오르고, 그 사람을 향한 관계 수치가 음수로 내려간다.
- **측정**: 사용자가 말한 기준. 예) 대화 상대의 스트레스 변화, 그 사람을 향한 관계 수치(−1~1). 엔진이 이미 기록한다(스트레스·기분은 inspect·체크포인트, 관계는 outcome 이벤트).
- **조작 점검**: 조작이 실제로 일어났는지 확인할 항목. 예) 그 사람이 실제로 부적절한 피드백을 했는가. 언어 모델은 무례한 역할을 순화할 수 있으므로, 이 항목이 없으면 "효과 없음"과 "연기 안 함"을 구분할 수 없다.
- **짝 연결**: baseline과 비교군이 같은 실험이라는 표시(실험 id). 변형 모드에서는 원본이 baseline이다.

## 7. md 자료

- 대화창에 붙인 md 파일은 업무를 만드는 근거가 된다(업무 이름, 내용, 결과물 형식·검토 기준, 선후 관계).
- 같은 내용을 시나리오의 `materials` 칸에도 넣어, 에이전트가 일하면서 참고할 수 있게 한다(내 판단).
- 자료가 없으면 실험 의도와 조직 설명만으로 만든다.

## 8. 저장과 초안

- 저장은 새 파일만 만든다. 기존 시나리오·프리셋을 고치지 않는다.
- 저장한 시나리오는 라이브 실행 목록(`/api/scenarios`)에 나타나야 한다. 지금 목록은 `experiment.SCENARIOS`(고정 목록)와 `runs.LEAD`에서 나오므로, 생성된 시나리오도 찾을 수 있게 해야 한다. 시나리오 목록 캐시는 `conf/` 파일 변경을 감지하므로 새 파일이 생기면 다시 만든다.
- 작업 중인 초안은 서버에 저장해, 브라우저를 닫아도 이어서 고칠 수 있게 한다(내 판단).
- 이름이 겹치면 새 이름을 받는다(덮어쓰지 않음).

## 10. 내가 정한 것 (사용자가 확인할 것)

- 생성 AI는 설정의 OpenAI 모델. Demo 설정이면 생성 버튼이 비활성(이유를 표시).
- 생성된 회사의 느슨한 규칙 세부(§4.1): 3~20명, 부서 최대 6개, 맨 위 보고자 한 명, 결재 단계를 안 적은 업무는 고정 표를 따름.
- 성향 규칙(§5.4): 요청한 사람에게만, 행동 묘사로, 비교 요인이 아니면 경고.
- 실험 정보는 시나리오 형식에 선택 칸 `experiment`를 더해 구조화(§6).
- 변형 요인 4가지로 시작(조직 구조 · 업무 · 성향 · 사건).
- 페르소나 스키마는 바꾸지 않고, 행동 성향은 서술형 칸에 적는다.
- md 자료는 업무 생성 근거 + `materials`에도 저장.
- "다른 점" 확인은 해석된 최종 설정끼리 비교, 범위 밖 차이는 경고 + 확인.
- 초안은 서버에 저장해 이어서 작업.
- 언어 기본값은 한국어, `prompt_style: human`(최근 r10 계열과 같음).

## 11. 빌더에게 맡기는 것

- 생성된 회사를 표시하는 방식, 결재 단계를 회사 파일에 적는 형식, 맵의 부서 자리에 새 부서를 배정하는 방법(§4.1).
- `experiment` 칸의 정확한 이름과 값 목록(§6).
- 생성 AI 프롬프트 설계와 생성 단계 나누기(한 번에 다 만들지, 회사 → 업무 → 일정 순으로 만들지).
- 자동 수정 재시도 횟수(무한 반복만 아니면 됨)와 실패 시 사용자에게 넘기는 방식.
- 생성 파일의 디렉터리 배치와 이름 규칙, 시나리오 목록에 넣는 방법.
- 서버 API 경로와 초안 저장 형식.
- 미리보기 각 탭의 세부 화면, 조직도 그리는 방식.
- 생성 한 번에 드는 토큰·비용을 보여 줄지와 그 형식.
